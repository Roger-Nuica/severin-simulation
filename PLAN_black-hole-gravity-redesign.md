# Plan: Black Hole gravitational-lensing visual redesign and positional sound

## Goal
Replace the Black Hole Gun's current look (flat core read, no lensing, round "bubble" particles, straight streaks, silent) with a gravitational-lensing-driven presentation — screen-space lensing, a volumetric core with a photon ring and a Doppler-beamed accretion disk, curved shard particles, and a full positional procedural sound layer — while leaving the fixed gameplay contract untouched: weapon on the wheel, `HOLE.seconds` 20 s, `HOLE.influence` 100 m pull, `HOLE.escape` 40 m no-escape, one-at-a-time behaviour, and the existing capture/spaghettify/dissolve/consume logic in `blackHole.js`.

## Clarifications needed
- None blocking. See **Note on the brief's "Problem" framing** below for a non-blocking discrepancy worth flagging.

## Note on the brief's "Problem" framing
A prior session's audit (this conversation, `PLAN_black-hole-visual-redesign.md` Subtask 1) found the current `look.js`/`matter.js`/`wind.js` to already be a shader-driven vortex (a logarithmic-spiral swirl shader, a black core sphere, additive particle streams), not literally "a flat disc cut into the image" or "big pink bubbles" — `matter.js`'s particles are soft round point-sprites coloured dust-brown→violet→white-hot, and `wind.js`'s streaks are already oriented boxes following the local inflow+swirl vector, not pure straight lines. This is not a `.claude/rules.md`-vs-runtime contradiction (no numeric gameplay contract is involved), so it is not a blocking gate — it is reported per the skill's reporting duty, not acted on. None of this changes the plan: every specific capability this brief asks for (screen-space gravitational lensing, chromatic aberration, a photon ring, a Doppler-beamed accretion disk, oriented/stretched "shard" particles, positional audio, reverse-reverb, world-audio ducking) is **absent from the current implementation regardless of how "current" is characterised**, so this plan builds all of it as genuinely new work on top of / replacing the relevant parts of `look.js`, `matter.js`, `wind.js` and a new sound module.

## Technical grounding (from this session's codebase research)
- **Post-processing hook**: `src/app/tornado/engine/post.js` is a hand-driven pipeline (not `EffectComposer`): scene → `Post.sceneTarget` (HDR, MSAA) → GTAO → `UnrealBloomPass` steps → one composite fragment shader that samples `tScene`/`tAO`/`tBloom` at `vUv` and draws straight to the canvas. The composite shader already runs once, full-screen, every frame — folding the lensing UV-warp + chromatic split into it (rather than a new render target + extra draw) satisfies "cheap, localised, skippable" at **lower** cost than a separate pass, since outside the hole's screen-space influence the extra ALU is gated by a `smoothstep` mask that costs ~nothing. This is a deliberate deviation from the brief's literal "separate half-res render target" suggestion, in favour of the project's own stated preference (post.js's header) for one hand-tuned pass over composer-style ping-ponging; it is flagged here, not hidden, since it changes *how* 1a is built, not what it delivers.
- **Shard/curved-trail particles**: `dissolve.js` already proves the exact technique needed — an `InstancedMesh` of small boxes, radius/angle/height kept per-fragment (not a velocity), oriented via quaternion along its direction of travel each frame and stretched (`s.set(sz/√long, sz/√long, sz*long)`) as it nears the hole. `matter.js` currently uses the shared round-point-sprite `particlePool.js` instead, which is camera-facing `gl_PointSize` only — it cannot be oriented or stretched, which is structurally why it reads as "bubbles." Replacing `matter.js`'s rendering with `dissolve.js`'s proven instanced-stretched-fragment approach (keeping its existing radius/angle physics, which already traces the shader's logarithmic arms) is reuse-of-the-closest-analogue, not a new technique.
- **Particle budget**: `perf/caps.js`'s shared `CAPS.particles` (10,000) / `particleRoom()` / `trackPool()` only tracks `particlePool.js`-style `THREE.Points` pools (it inspects `geometry.attributes.aColour`/`aSize`). `dissolve.js`'s `InstancedMesh` fragments are **not** in that shared budget — they carry their own fixed ceiling (`DISSOLVE.maxFragments` 1400) instead, same as `wind.js`'s streaks. The replacement shard system for `matter.js` must follow the same self-contained-cap pattern, sized at or below the current `MATTER.max` (2400), rather than being registered with `caps.trackPool()` (wrong pool shape) or left uncapped.
- **Positional audio**: `sound/creatures.js` already implements exactly what §2 asks for — a pool of `CREATURE.voices` (18) reusable `PannerNode` voices (equal-power, inverse distance), a listener that follows the camera every frame, per-kind minimum gaps, quietest-voice-stolen-when-full, and a settings toggle (`engineCtx.systems.settings.get('creatures')`). This is the pattern to reuse for the hole's drone/wind/whine/swallow voices, rather than inventing a new positional-audio system.
- **Reverse-reverb**: no `ConvolverNode` or reverb of any kind exists anywhere in `sound/`. This is genuinely new to the codebase (see risk note on Subtask 9).
- **World-audio ducking**: `sound/index.js` already has exactly the mechanism asked for — a master `SoundSystem.muffle` lowpass between `masterGain` and the listener, driven today only by `setMuffle(amount)` from `player/abilities.js` (Bullet Time, `amount` 0 or 1, called on transition, not every frame). Calling `setMuffle` every frame from the Black Hole as well would fight Bullet Time for the same single knob. The minimal, source-compatible fix is to make `setMuffle` combine multiple named contributions (`Map<string, number>`, combined by `Math.max`) instead of overwriting a single value — existing call sites (`abilities.js`'s `setMuffle(1)`/`setMuffle(0)`) keep working unchanged under a default key. This touches a shared file outside `player/blackHole.js`; flagged per the skill's "no hidden out-of-scope fix" rule, but it is a small, additive, backward-compatible change, not a gameplay-contract change.
- **Performance fallback**: `engine/quality.js` already is the project's single adaptive-quality ladder (`qualityStep()` 0..4, monotonically down, driven by a real measured FPS average) — `scene.js`/`post.js` already read it to drop pixel ratio, AO, MSAA, shadow size. The brief's "if FPS drops, reduce lensing resolution/particle count" is satisfied by reading `ctx.systems.quality.qualityStep()` in the new code and scaling the lensing mask radius / shard emission rate down at higher steps, rather than building a second, parallel FPS watcher (which CLAUDE.md's "do not introduce global state or duplicate central systems" rule would forbid).
