# Plan: Co-op guest fixes (weapons in aim mode, laggy movement)

## Goal
Make the co-op guest (ROGER 2) a first-class player: (1) raising the weapon (right-click) shows the weapon in the guest's hand, and every weapon on the wheel can be fired with feedback the guest and the host can both see; (2) guest movement feels immediate (client-side prediction with reconciliation) while the host stays the single authority. No regression for the host, health (R-053), the enemy-immunity contract or the weapon wheel (R-049).

This plan contains no production code. Nothing below has been run in two browsers: where a cause is a hypothesis it says so and a diagnostic subtask comes first. The user's answers of 2026-10-05 are recorded under Clarifications.

## Root-cause findings

### (a) Guest weapon never appears, and firing gives nothing to see
Confirmed from code (file:line from `net/system.js` unless stated):
1. **No weapon is ever drawn for a guest.** The peer's own player proxy is `makeRogerProxy` (lines 1117-1129): a dressed person figure with no weapon part. While aiming, `updatePeer` hides that proxy (`own.visible = !camPose.firstPerson`, ~1247) and moves the camera to the eyes (`followCamera`, `rogerView.js` `aim` branch). The only first-person weapon models (`view()`, `showView`, `placeView` in `heroWeapons.js` ~546-590) belong to the host's own `heroWeapons` instance, are placed in the host camera's frame, and are never built for a guest. The snapshot carries each player's weapon index (players row column 5, `buildSnapshot` ~950) but `updatePeer` never reads it. Result: crosshair only, nothing in hand, matching the screenshot.
2. **A guest's shot has no visual or sound on either machine.** `guestFire` (841-921) resolves rifle/minigun/railgun as an instant `scan()` ray plus `enemies.hit`, the Katana as an arc test, and only the Fire Gun (`hero().guestFlame`) and Black Hole (`blackHole.fire`) produce any effect. No tracer, muzzle flash, bullet or sound is spawned, and the peer's own simulation is idle. A working shot therefore looks like "nothing to shoot with". The wire cannot carry an effect either: `EVENT_TYPES` (`protocol.js:57`) has no shot event.
3. **Latent hard stop: yaw is never wrapped.** `S.look.yaw -= movementX * sensitivity` (mousemove handler, ~1373) grows without bound, but `validateInput` rejects `|yaw| > 4*PI` (`protocol.js` ~108, "yaw" error) in the relay (`relay/server.mjs` input case) and again in `inputGate`. After about two full turns of mouse look every input is rejected (the client only records `error`, `client.js` 'error' case), so movement, aim and fire all freeze for the guest. This alone can read as "the weapon does not fire".
4. **Fire is a level, sampled at 30 Hz.** `S.buttons.fire` is sent as a boolean every 33 ms (`updatePeer` ~1185) and the host keeps only the latest input (`hostMessage` 'input'). A click shorter than one input interval (or lost to a coalesced frame) is never seen by the host; the 'left click while not pointer-locked only requests the lock' branch (`mousedown` handler) swallows the first click.
5. Host side gating is `ctl.aim && input.fire` (`updateGuests` ~700), where `ctl.aim` means "player is up and not seated" (`players.js` `controls`, line 231). It does NOT test `input.aim`, so the guest can fire without the weapon raised, unlike the host's own flow (raise, then fire; `heroMode.js` header). This is a behaviour mismatch, not a cause of the symptom.

Hypotheses (not confirmed): the host's `guestFire` may not be reached in the reporter's setup for a reason not visible in code (host not in Hero Mode: `updateGuests` removes avatars and skips input when `rogerPose()` is null; WASD working suggests it is running). A diagnostic counter (Subtask 1) settles whether `guestFire` runs, which weapon, and whether `enemies.hit` returns true.

### (b) About one second of guest movement latency
Confirmed architecture facts:
- **There is no client-side prediction.** The guest camera follows the guest's own snapshot row (`s.kinds.players.get(myId)`, `updatePeer` ~1236). A key press travels: peer frame (up to 33 ms input interval) -> relay (WebSocket) -> host (`p.input`), applied at the host's next frame in `moveGuest` (775-798) -> host `buildSnapshot` at 15 Hz (`SNAP_INTERVAL` 67 ms, sent only inside a host frame) -> relay -> peer, which renders `INTERP_DELAY` 0.14 s behind the newest snapshot (`interp.js:15`). The floor is roughly one full RTT + ~33 + ~67 + 140 ms. At 150 to 300 ms RTT that is about 0.4 to 0.7 s of pure input lag before any jitter.
- **The relay is a remote Render free-tier process, not Vercel.** Vercel serverless cannot hold the WebSocket (the app reads `NEXT_PUBLIC_RELAY_URL`, `system.js:82`, default `ws://localhost:8787`; `PLAN_coop_two_rogers.md` records the relay at `https://severin-relay.onrender.com`). Its region, cold starts and TCP/proxy buffering add to RTT and jitter. Relay forwarding itself is cheap (`relay/server.mjs`, no polling or batching).
- **Clock-offset estimator tracks, not minimises.** `interp.js` `push` clamps `offset` to within +/-0.05 s of the latest sample (`Math.min(offset + 0.05, Math.max(offset - 0.05, candidate))`), though its comment says "min over the window". Under jitter the render time wanders, adding stutter and sometimes extra delay. Fact from code; effect size unmeasured.
- **Host frame rate bounds everything, but throttling is ruled out.** The host applies inputs and sends snapshots only inside its frame (`updateNet`), and `tornadoEngine.js:902` clamps the frame delta to 0.05 s. The earlier hypothesis (a background host tab throttled to about 1 frame a second) is effectively ruled out: the user, 2026-10-05, tested on two different computers with the host window in the foreground. The host still runs at its own frame rate, so a heavy host frame would add delay; Subtask 1 logs host frame delta to exclude it.
- **Remaining candidates for the ~1 s (all unconfirmed until Subtask 1 reports):** (i) real RTT and jitter through the Render free-tier relay (region distance, cold or slept instance, proxy buffering); (ii) relay or socket buffering, such as Nagle, per-message compression or batching in the Render proxy (`relay/server.mjs` sets no `perMessageDeflate` or `noDelay` option and has no tick or flush logic beyond the 1 s `registry.tick()` housekeeping, so it forwards each frame as received; whether the platform proxy batches is unknown); (iii) the absence of prediction, which adds a full RTT + 33 + 67 + 140 ms floor to every key; (iv) the offset-estimator jitter above. Rate-limit buckets in the relay (`inputs` 40/s, `hostOut` 60/s) drop silently when a TCP stall releases a burst, which would make catch-up feel like extra lag.

Conclusion: even in the best case the current design cannot feel immediate; prediction is required. How much of the reported ~1 s is real network/relay delay versus estimator jitter is unconfirmed and is measured first (Subtask 1).
