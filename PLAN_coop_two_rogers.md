# Plan: Co-op "Two Rogers" and online deployment

## Goal
Let the guest play Roger exactly as the host does (same Roger model, HUD and third-person Hero Mode flow, each player with their own camera), with both players able to hurt each other through `health.damagePlayer`. Make Hero Mode work in a room for both roles, and deploy the relay and the app so two people can play fully online. The host browser stays the single authority; the peer simulation stays idle. This plan contains no production code and approves no provider.

## Baseline (verified in the repository, 2026-10-02)
- Host runs the authoritative simulation. Peer keeps its local sim idle and draws host snapshots as proxies (`net/system.js` `updatePeer`, `makeProxy`). `makeProxy('players')` is a capsule; the guest's avatar on the host exists only while the host is in Hero Mode (`updateGuests`: `if (!heroOn) removeAvatar`).
- The peer's Hero and Start buttons are disabled (`enterPeerView`, ~line 909). `startSession` refuses to host or join while `ctx.Hero.active` (~lines 219-226). The peer takes pointer lock on `mousedown` on the canvas (~line 1135) while `Sim.three.controls` (OrbitControls) is only disabled, not detached, which is the likely source of the `setPointerCapture` console error.
- Friendly fire is already ON (`FRIENDLY_FIRE = true`, R-053, R-013, R-031). The "Friendly fire: disabled" decision 7 and clarification 7 in `PLAN_coop.md` are stale and contradict `.claude/rules.md`. Per `CLAUDE.md`, `.claude/rules.md` is the implementation source, so this is reported, not reconciled silently.
- Relay (`relay/server.mjs`) is a standalone `ws` process that imports `room.js` and `protocol.js` from `src/`. `ALLOWED_ORIGINS` empty means every Origin is accepted. Control frames are rate-limited per connection only (5/s); there is no per-IP limit. Invite codes are 6 characters from a 31-character alphabet, so there are roughly 8.9e8 codes; rooms idle out after 30 minutes. `RELAY_URL` defaults to `ws://localhost:8787` and is overridden by `NEXT_PUBLIC_RELAY_URL`, which Next.js inlines at build time.
- Documentation drift to report: `CLAUDE.md` says Next.js 16.3.5; `package.json` pins 16.3.8. `PLAN_coop.md` shows Subtasks 3 to 11 unchecked although `net/`, `relay/` and tests (`protocol`, `room`, `client`, `relay.integration`, `coop-rules`, `friendly-fire`, `melee`, `health`) exist.

## Approved decisions (two Rogers) — user, 2026-10-02
1. **Guest as Roger:** presentation-only Hero view on the peer (Roger model, own third-person camera and HUD) driven by host snapshots; the peer's local Hero state machine does not run.
2. **Starting Hero Mode:** the host presses Hero as usual. The guest has the same Hero button and presses it too; both live in the same world and can fight. (Supersedes the "Join as Roger" wording.)
3. **Outcome:** players always revive. If the guest leaves, the host's game is unchanged and continues; if the host leaves, everything ends (no host migration, as before).
4. **Respawn:** a downed player respawns by pressing Start (no score for downing the other Rogers is assumed unless the user says otherwise).
5. **Protocol version:** delegated to the senior engineer: bump `PROTOCOL_VERSION` to 2 only if a new field is genuinely required, and make the relay reject mismatches with a clear "refresh the page" message.
6. **Time Slow and EMP for the guest:** to be added. The user wants Time Slow not to affect the other player's perspective. **Conflict to resolve in Subtask 2:** the approved shared decision was one host-authoritative time scale. A guest-only slow-motion would need per-player time (own avatar, own camera and own weapons slowed, world unchanged) and must be designed and approved before coding. Do not silently reinterpret either rule.
7. **Deployment:** Render has been proposed (see `docs/deploy.md`, Subtask 7); account ownership still to be confirmed.

## New defects reported by the user (must be fixed; add to Subtask 3/6 acceptance)
- **D1 Pointer-lock error:** `Pointer lock cannot be acquired immediately after the user has exited the lock.` The peer requests lock again straight after the browser released it (Esc). Needs a short retry guard (do not request within about 1.5 s of `pointerlockchange` exit, or request only on a fresh click after that delay) and a handled promise rejection. Same family as the `setPointerCapture` error in Subtask 6.
- **D2 Guest-started tornado is a separate world:** the guest pressed Tornado in its own idle local simulation, so the host never saw it. On a peer, every world-affecting UI control (Tornado, disasters, presets, storm, Reset, Pause and similar) must either be disabled or sent to the host as a validated request that the host applies to the one authoritative world. Decide per control in Subtask 2; the default is to disable them on the peer and route only Hero, Tornado and Pause as host requests after approval.

- **D3 Guest screen blocked (reported 2026-10-02, online via Render/Vercel):** after entering the invite code the guest cannot move the mouse or do anything. Investigate `enterPeerView`/`restorePeerView`, `controls.enabled = false`, pointer lock and overlay/pointer-events in `net/system.js` and `tornado.css`; the peer must have a working view (look/move/UI) as soon as the welcome arrives, with an explicit way out (Leave) that restores single-player controls.
- **Deployment status:** relay live on Render (`https://severin-relay.onrender.com`, free tier, `ALLOWED_ORIGINS` = the Vercel origin); game on Vercel with `NEXT_PUBLIC_RELAY_URL=wss://severin-relay.onrender.com`. Host and guest connected online successfully (invite code flow verified by the user). Subtask 7 therefore reduces to documenting this in `docs/deploy.md` and relay hardening.

## Clarifications needed (decision gates; block the dependent subtask until answered)
1. **Guest "Roger" architecture (blocks Subtask 2).** Recommended option A: the peer runs a presentation-only Hero view. It reuses Roger's model, HUD and third-person follow camera, positioned from the interpolated snapshot row for the peer's own id plus light local prediction, and sends the same input messages as today. The peer's local `heroMode` state machine (phase, timer, pursuers, bunker) does NOT run. Option B: run the full local `heroMode` on the peer. Not recommended: it breaks the idle-peer-sim design and invites divergence from the host's town, Terminators and damage. Confirm A.
2. **Who may start Hero Mode in a room (blocks Subtasks 2, 3).** Option A (recommended): the host's Hero button starts the shared run; the guest's Hero button becomes "Join as Roger", enabled once the room is open, and the guest spawns when the host is in Hero Mode (or immediately drops in beside the host if already running). Option B: creating or joining a room auto-starts Hero Mode for the host. Option C: each player may start and exit independently. This needs a decision because exiting Hero Mode currently removes every guest avatar and the run end (bunker SAFE, `HERO.endSeconds`) is global.
3. **Shared outcome rules (blocks Subtask 3).** When Roger '0' (host) dies or the bunker is reached, does the run end for both? Existing rule: both down means game over, via `net.interceptRogerDeath`; confirm that this stays, and confirm that the bunker "SAFE" win applies to both players (either player reaching it, or both).
4. **Player-versus-player scoring (blocks Subtask 4).** Does a kill on the other Roger score points or only down the target (current kill paths give no points for downing a player)? Is there a down-and-revive window against a human enemy as it is for Terminator kills (REVIVE 5 s / 3 m)? Is the 3 s spawn shield and 2 s revive shield enough protection against spawn-camping?
5. **Hosting and deployment (Subtask 7).** See Decision Gate D below. No provider is chosen.
6. **Protocol versioning (blocks Subtask 2 if a new field is needed).** If the guest needs a new "enter Hero" intent field in `input` or a new control message, `protocol.js` validators accept only listed fields. Approve bumping `PROTOCOL_VERSION` to 2 (host and peer must then run the same build) or constraining the design to the existing messages.

### Decision Gate D (deployment; the user must pick; recommendation stated, nothing provisioned until approved)
- **D1 Relay host (needs a long-lived WebSocket process, so not a short-lived serverless function).**
  - (a) Small container host with native WebSocket support and TLS termination (for example Fly.io, Railway, Render): simplest, cheap, public `wss://`. Recommended in principle.
  - (b) A VPS running the relay under a process manager behind a reverse proxy (Caddy or nginx) with a Let's Encrypt certificate: most control, most operations work.
  - (c) A managed realtime service replacing the custom relay: contradicts the approved decision 1 (custom `ws` relay) and needs a rewrite; listed for completeness only.
  - Vercel Functions are not recommended for the relay (stateless, request-scoped); verify the current WebSocket limits in Vercel's documentation before ruling it in or out.
- **D2 Next.js app host.** (a) Vercel (natural fit for Next.js; the app needs no server state, the relay is separate): recommended if D1 is a container host. (b) The same container or VPS as the relay (one provider, one invoice). The app is served over HTTPS in either case, so the relay MUST be `wss://` (browsers block `ws://` from an HTTPS page as mixed content). `NEXT_PUBLIC_RELAY_URL` is baked in at build time, so each environment needs its own build or variable value.
- **D3 Origin policy.** Set `ALLOWED_ORIGINS` to the exact deployed app origin(s) (comma-separated). Note an Origin check only stops other websites, not scripted clients; it is not authentication.
- **D4 Invite-code security.** Recommended minimum: keep 6-character codes; add per-IP connection and join-attempt rate limits and a failed-join lockout in the relay; consider lengthening to 8 characters; log nothing sensitive; rooms already expire after 30 minutes idle. State that the code is the only credential (approved decision 1) and the room holds two players.
- **D5 Operations.** Who owns the account, budget, region (choose near both players), health check path, and restart policy.

## Known risks across the plan
- The largest risk is the idle-peer design: any local Hero state on the peer must be presentation-only. If decision 1 selects option B, re-plan; it is a different, riskier architecture.
- Protocol changes break host and peer compatibility during a deploy; bump `PROTOCOL_VERSION` and deploy relay, app and both players on the same build.
- The relay is a single in-memory instance and a public endpoint: hardening in D3 and D4 is required before sharing a URL beyond people you trust.
